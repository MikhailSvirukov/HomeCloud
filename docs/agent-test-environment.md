# Задание агенту: тестовая среда

См. [общую спецификацию](specification-v1.md). Подготовить воспроизводимую среду для проверки Android-клиента, выделенного сервера и многоузлового кластера. Исходные целевые технологии — Android на Kotlin/Jetpack Compose, серверы на Rust.

## Требования

- Поднимать выделенный сервер и параметризуемое нечётное число storage-узлов с изолированными данными и стабильными node ID/labels/ключами.
- Создавать изолированную Docker TCP-сеть для тестового кластера, включая прямые storage-to-storage каналы для Raft и репликации blobs.
- Поддерживать два базовых класса отказа: (1) полное выключение узла — остановка/завершение его контейнера; (2) программный сетевой сбой — выборочная блокировка или деградация соединений между заданными парами узлов с настройкой задержки, потерь и восстановления связи.
- Управлять сценарием отказа и восстановлением из Rust-кода тестов, без обязательных shell/Python orchestration-скриптов. Можно использовать Testcontainers for Rust и Rust-клиент к отдельному fault-injection proxy; конкретную реализацию закрепить в тестовом проекте.
- Предусмотреть расширяемый API сценариев отказа, чтобы добавлять проверки автоматического восстановления и других будущих функций без переписывания стенда.
- Поддерживать Android emulator или подключаемое физическое Android-устройство и тестовый набор фото/видео с разными размерами/метаданными.
- Иметь воспроизводимую процедуру первичного bootstrap фиксированного кластера и выдачи топологии клиенту.
- Проверять регистрацию login, распространение password verifier и клиентского открытого ключа, отказ от повторно занятого login.
- Проверять шифрование/подписи запросов и ответов, проверку node labels, отказ при неверной подписи и изменённом закреплённом ключе. Проверять регистрацию через TOFU и зафиксировать, что активная подмена при первом контакте входит в принятую модель риска.
- Проверять первичную загрузку медиатеки, новые и изменённые файлы, сохранение старых версий, исключение аудио и идемпотентный retry.
- Проверять кворумные сценарии при обоих видах отказа: потеря одного узла, отсутствие кворума, timeout на commit, отсутствие ответа после успешного commit и повтор с тем же `upload_id`.
- Проверять выборочное сетевое разделение: узлы остаются запущенными, но заданные peer-соединения недоступны; после восстановления связи кластер возвращается к согласованному состоянию.
- Проверять возврат узла: догонка Raft-журнала/snapshot и файловых blobs, проверка хэшей и переход в синхронизированное состояние.
- Проверять heartbeat выделенного сервера отдельно от Raft heartbeat и отсутствие распространения health-статуса в клиентскую топологию.
- Уметь останавливать/перезапускать компоненты и очищать стенд без потери возможности повторить сценарий.
- Для Rust-моков читать публичные `pub trait`/типы crate-ов storage-node и dedicated-server; создавать mock/fake-реализации только по этим публичным контрактам. Не привязывать тесты к приватным модулям и деталям реализации; если публичного trait/API недостаточно, оформить запрос владельцу компонента. Для Kotlin использовать опубликованные protocol/API интерфейсы.
- Разделять быстрые изолированные тесты с mocks/fakes и интеграционные сценарии с Docker-контейнерами; не требовать Docker для каждого unit/component-теста.
- Изолированно проверять пулы крупных файловых payload-буферов (без заголовков/metadata): выбор/балансировку размерных классов, лимиты памяти, backpressure при исчерпании, возврат буферов, цепочки блоков, последний неполный блок и конкурентные запросы.
- Проверять потоковую загрузку файла, превышающего максимальный размер одного буфера, разрыв посреди передачи и полный повтор с тем же `upload_id` без resume.

## Не входит

Проверка динамического добавления узла, ротации ключей, resumable chunks, админ-панели и режима single-node без Raft до появления этих функций в будущих релизах. Стенд при этом должен позволять добавлять для них новые fault/recovery-сценарии.
