# Global agent instructions

These instructions apply to all four workstreams and are copied with the public monorepo into each workstream clone. The shared project boundary consists of this file, `docs/specification-v1.md`, the shared architecture and cross-cutting SRS in `docs/specification-v1.md`, the shared normative `docs/specification-v1/protocol-details.md` and `docs/specification-v1/configuration-profile.md` appendices, and only the assigned area SRS file in `docs/specification-v1/`, the assigned workstream brief and role file, explicitly published API/protocol contracts under `contracts/`, root `AGENTS.md` for Rust practices, and daily review files mounted read-only. Other workstream briefs and role files are not shared context.

## Workstream ownership and read scope

Each workstream has its own clone of the same monorepo and its own checkout, branch, OpenCode state, and task history. Use the same configured Git author/committer identity in all four clones. Do not use another workstream's clone or checkout.

The workstream map is:

- `android/`: Android client and Android tests; SRS `docs/specification-v1/android.md`.
- `distributed-server/`: distributed Rust storage nodes and their component tests; SRS `docs/specification-v1/storage-cluster.md`.
- `dedicated-server/`: Rust registration/bootstrap/control-plane service and its component tests; SRS `docs/specification-v1/dedicated-server.md`.
- `test-environment/`: Rust test harness, Docker scenarios, shared test utilities, mocks, and fakes; SRS `docs/specification-v1/test-environment.md`.

The assigned orchestrator owns its mapped area and must use its area SRS together with the shared architecture; other area SRS files are not part of its implementation context. The `dedicated-server` workstream additionally owns repository-wide shared files, including root-level files and directories such as `.github/`, `.opencode/`, `contracts/`, and shared `docs/` files. This includes shared specifications, global instructions, repository configuration, CI workflows, and container/Compose setup. It does not include files under `android/`, `distributed-server/`, or `test-environment/`, or another workstream's area SRS and brief. When a shared-file change is needed, assign its issue to `area:dedicated-server` and `agent:claimed/dedicated-server`; the dedicated-server orchestrator names the exact shared paths and may delegate only those paths. Other workstreams may read shared context but must not edit shared files; they report the required path and dependency so the change can be routed to dedicated-server. A task spanning shared files and an area implementation is split into separately owned tasks/PRs unless the dedicated-server task is limited to the shared change.

Each orchestrator may delegate only tasks inside its ownership scope to its own worker subagents, and workers may read and change only files in their assigned task paths. The reviewer receives the same scope and may inspect the complete diff for that workstream only. The orchestrator must define explicit file/path ownership before delegating and must not ask a worker or reviewer to inspect another workstream's implementation.

Ownership confirmed by the operator on 2026-10-30: `dedicated-server` is the sole owner of the shared SRS, `contracts/`, and repository-root instructions/configuration. Each workstream retains ownership of its area SRS and implementation. The 2026-10-28 review note assigning shared documents to distributed-server is superseded; do not use historical feedback to reroute shared changes. Other workstreams create dependency issues for dedicated-server naming exact paths and requirements, then continue independent tasks.

The operator may run different workstreams concurrently, each in its own container/clone with separate session/state/report directories. Never run two orchestrators against the same workstream checkout at once. Each orchestrator claims only its area issues; shared changes belong exclusively to dedicated-server. Split cross-area issues by ownership before claiming them. Labels are coordination signals, not atomic locks. Historical one-workstream-per-day guidance is superseded; it must not prevent an already started workstream from proceeding or polling another workstream's dependency.

## Normative requirements and task formation

The applicable area SRS plus `docs/specification-v1.md` and its normative `docs/specification-v1/protocol-details.md` and `docs/specification-v1/configuration-profile.md` appendices are the sole sources of product requirements. The appendices are shared design owned by dedicated-server; every workstream may read them. Include their IDs and revisions when reconciling the requirement backlog. Schedule implementation only for requirements marked `MUST / Утверждено`; do not implement behavior that depends on an unresolved `OPEN` decision before its decision is recorded in a merged SRS change. An unresolved `OPEN` item is not, by itself, a reason to stop a workstream: the orchestrator must resolve it through the specification-decision process below, split out the dependent implementation, and process the decision PR through the normal review and CI cycle. If that cycle is externally blocked, park it with evidence and continue independent eligible work within the one-active-cycle rule. Published API/protocol contracts may refine wire representation only where the SRS delegates those details to a contract. This file, area role briefs, GitHub issues, PR descriptions/comments, code, and daily review notes describe workflow or context; they do not add product behavior or acceptance criteria.

Before delegating implementation or test work, the orchestrator must identify exact requirement IDs and revisions from the SRS. It then creates one or more bounded tasks, each naming the requirement IDs it covers, assigned paths, expected change, and relevant verification. Multiple tasks may cover one requirement when they have disjoint responsibilities; one task may cover several requirements when they form one coherent change. Every code or test change must trace back to the cited requirements, and the reviewer checks that traceability in the PR.

Agent containers must not execute unit, integration, acceptance, instrumentation, Docker, or fault-injection test suites locally. Workers must add or update the tests specified by the task and publish the PR without running them. GitHub Actions on the PR is the authoritative automated test result. The orchestrator must inspect the required check runs through GitHub Actions MCP and must not merge while a required check is pending, failing, missing, or skipped for the changed area. Local source inspection and non-test checks such as formatting or linting may still be used when useful; they do not replace CI.

An issue is a work request, not a normative requirement. The orchestrator may pick it up only when it maps to existing SRS requirement IDs or is an explicitly scoped repository/process-maintenance task. The orchestrator is authorized to resolve product and implementation decisions needed to complete the system without asking the operator for approval. When behavior is absent, ambiguous, incomplete, or conflicting, it must choose the narrowest safe behavior consistent with accepted requirements, prior decisions, the v1 scope, and platform/security guidance. It must record the decision, rationale, relevant alternatives, and impact in a separate specification-change PR, updating or adding uniquely identified and objectively verifiable SRS requirements with owner, source, status, and verification criterion. The PR description must explain the decision in enough detail for the owner to understand it; it must not wait for owner approval. After internal review and required CI pass, the orchestrator merges the specification PR, then creates or resumes the separate implementation task/PR against the merged requirement IDs and continues work. Keep at most one active issue/PR cycle at a time. Review and CI waiting belong to that cycle; if an external condition prevents it from proceeding, park it with evidence before activating another independent task. It must not mark a whole workstream blocked merely because a dependent decision or external contract is pending: identify the exact dependent requirement IDs, route or publish the needed contract/decision with its owner, and continue unrelated work. If a technical or operational fact cannot be inferred safely, choose a conservative v1 fallback, document the limitation, and continue; use the dependency-waiting policy below if other workstreams are pending, and stop for an external blocker only when it prevents both safe work and dependency polling.

An SRS change must explicitly name the SRS file and assign it to one workstream. An area SRS is owned by its mapped workstream. Shared `docs/specification-v1.md` is owned by the dedicated-server workstream; its changes require an issue assigned to that workstream. Do not let multiple workstreams edit shared requirements concurrently. The specification-change task is subject to the same path, review, and PR workflow as implementation work.

Daily review notes and GitHub review comments remain valuable process feedback. They may guide implementation style, task planning, and review emphasis, but a requested product behavior becomes binding only after it is recorded in the SRS and merged. A code review must flag behavior that has no SRS basis, even if an issue or note requested it. The orchestrator must keep the system moving: it resolves open decisions, completes the requirement PR, then continues implementation and subsequent in-scope tasks until the system is complete or the configured per-invocation task/time budget is reached. It must not wait for operator approval between decisions, requirement PRs, implementation PRs, or task cycles.

### Invocation budgets and stop reasons

The current container environment values `AGENT_MAX_TASKS` and `AGENT_MAX_RUN_SECONDS` are the authoritative per-invocation budgets. Either limit may end the run independently. Defaults quoted in documentation or daily feedback do not override these values. At every invocation, including `--continue`, read the current values, record a fresh start timestamp, and reset the claimed-issue counter. Previously saved session timestamps, deadlines, and counters belong to the previous invocation. Time spent waiting for review or CI counts toward the current elapsed time. Authorization to make decisions does not waive these budgets.

Before stopping, record the start and end timestamps, elapsed seconds, effective time/task limits, number of issues claimed, and exactly one reason in the state file and final report: `time_limit`, `task_limit`, `no_remaining_work`, or `external_blocker`. For `no_remaining_work`, reconcile outstanding approved SRS requirements as well as existing issues; create the next bounded task when requirements remain, even if no issue already exists. For `external_blocker`, name exact dependent requirement IDs, evidence of the blocking condition, and why neither independent implementation nor an authorized specification-decision task can proceed. If the current time/task budgets remain and independent work exists, continue work.

Use `time_limit` only after measured elapsed time reaches `AGENT_MAX_RUN_SECONDS`. Do not stop early merely because the next task might not finish in the remaining time. Split the next task or checkpoint unfinished work, including an unmerged branch/PR, at the actual limit; normal review and CI merge gates remain mandatory.

### Waiting for another workstream

If remaining work depends on another workstream, first refresh the relevant dependency issues/PRs and fetch the current default branch. Inspect only shared SRS/contracts and own-area paths, using remote file revisions without overwriting a dirty checkout. An old state-file blocker is not evidence that the dependency is still open. A closed issue alone is insufficient: verify that the required contract/decision/artifact has actually been published in the merged version before resuming its dependent implementation.

Route a missing contract to its owner with exact paths and requirement IDs, then continue independent work or authorized specification decisions. Once no independent task remains, stay in this invocation and periodically recheck the pending dependencies until one becomes available or a time/task limit is reached. `AGENT_DEPENDENCY_POLL_SECONDS` sets the interval (positive integer seconds; default 60); use 60 if absent or invalid and record that fallback in the run report. Waiting counts toward elapsed time, does not claim another issue, and does not reset the invocation clock. Wait no longer than the remaining time budget, using chunks of at most 60 seconds so the agent can respond to operator input. Avoid polling continuously. A newly available dependency resumes normal work without operator approval.

Record the dependency, owner, issue/PR and required artifact, latest check timestamp/result, accumulated waiting time, and effective polling interval in the existing run report and state file. Update this compact summary during waiting. Pending dependencies mean the run is still `running`; they are not `no_remaining_work` or an immediate `external_blocker`. If the budget expires while waiting, finalize with the actual limit reason and list pending dependencies. Reserve `external_blocker` for an external condition that prevents both safe work and dependency polling, with concrete evidence. This waiting policy supersedes historical feedback allowing immediate exit for cross-workstream dependencies.

### Reviewer publication fallback

The independent reviewer normally publishes its own GitHub `COMMENT` review. If publication fails, it must retry through its permitted GitHub MCP tools and check whether the first attempt succeeded before creating another review. If it still cannot publish, it returns the exact final review text, verdict marker, PR number, reviewed head commit SHA, any inline findings with their locations, and the sanitized error/attempt history to the orchestrator. This fallback transfers publication only; the review must still be performed by the independent reviewer.

The orchestrator may then publish that review as a GitHub `COMMENT` review through its authorized review tools, with the reviewer text unchanged. Add a separate attribution stating that the orchestrator is publishing on behalf of the reviewer because publication failed, and include the reviewed commit SHA. Verify the PR head still equals that SHA before publication and before accepting the review for merge. A changed head requires a new independent review. Preserve `changes-requested` as such; do not invent an approval or remove findings. Required CI gates remain unchanged. If the orchestrator also lacks an authorized publication tool, record the failure and park the cycle; do not merge an unreviewed or unpublished verdict. Record fallback use, errors, reviewed SHA, and the resulting review URL in the run report and state file. On the next review, attempt direct reviewer publication again.

### Reports to the operator

If an optional feedback pointer such as `.agent-feedback/latest-review.md` is absent or broken, report that fact and read the newest dated review files plus standing guidance directly. Do not stop an otherwise valid invocation solely because that convenience pointer is missing. Missing shared instructions or contracts must be handled separately under the normal dependency policy.

The orchestrator must create one Markdown report per invocation in `/workspace/.agent-reports/`, using the shared [run report template](agent-run-report-template.md). This is a writable mount of only this workstream's host report directory, separate from the read-only operator feedback. All workstreams may read the shared template; writing their own report is authorized workflow bookkeeping and does not require a shared-file issue. Do not inspect other workstreams' reports. Workers and reviewer must return difficulties, unclear instructions, and decisions to their orchestrator for inclusion in the report.

At startup, create a new file named `<UTC-start-YYYY-MM-DDTHH-MM-SSZ>-<run-UUID>.md`, record the effective budgets, and set its status to `running`. Use a new UUID and file even when continuing a session. Update that same file at safe checkpoints, after significant failures and issue/PR cycles. Before every normal exit, finalize it with status `finished`, timestamps, the stop reason and evidence required above, completed work, unresolved ambiguities, decisions and linked SRS PRs, technical failures, dependent requirement IDs, attempted remedies, independent work considered, and the next concrete action. Use `none` explicitly for empty sections; distinguish observed facts from suspected causes. Write report prose in Russian, preserving code identifiers and links.

Do not overwrite reports from other invocations or commit reports to Git. Keep credentials, tokens, private keys, file payloads, and unnecessary personal data out of reports. Record the report path in `.agent-state/project-state.md` and the final terminal summary. If the report cannot be written, explain the filesystem error in the terminal and state file without marking reporting successful; continue independent work. A force-kill or host failure may prevent finalization, so startup and checkpoint updates must leave a useful partial report with status `running`.

### Empty-repository bootstrap ownership

The repository may begin empty. During an explicitly assigned bootstrap issue, an orchestrator may create its own mapped top-level directory (`android/`, `distributed-server/`, `dedicated-server/`, or `test-environment/`) and add that area’s manifests, local `AGENTS.md`, starter documentation, and area-local CI scripts/configuration. Keep the Android Gradle project and each Rust Cargo workspace rooted independently in their mapped directories; do not combine them into a root workspace. The test-environment bootstrap uses only the v1 specification and published contracts to establish mocks/fakes and a harness skeleton.

Root-level and other repository-wide shared files (including root `AGENTS.md`, README, common configuration, `.github/workflows/`, `.opencode/`, `contracts/`, shared `docs/`, and container/Compose files) are owned by the dedicated-server workstream. Every issue for such a change must name the exact paths and be labeled for `dedicated-server`; only that workstream may claim, edit, and review the shared-file change. GitHub Actions workflow YAML belongs under `.github/workflows/`; workflows there should call the area-local CI checks rather than relocating component configuration into another area. This ownership does not grant permission to browse or modify Android, distributed-server, or test-environment implementation. Do not have multiple workstreams initialize the same shared files concurrently.

Do not browse, search, list, summarize, or adapt to source files owned by another workstream. A need to change a shared contract or cross-workstream interface is raised as an issue/PR for the owning workstream; do not inspect its private implementation to solve the integration. Treat root build files, dependency manifests, and shared code as shared scope: read or change them only when the task requires it, explain the dependency to the operator, and keep changes narrowly scoped.

The test-environment workstream may inspect only public Rust traits/types and public Kotlin API/protocol interfaces needed to build mocks, fakes, or integration tests. It must not inspect private component implementations. If an interface is not published as a stable contract, create an issue for the owning workstream to publish it and continue with independent work; do not ask the operator to resolve the routine ownership or contract gap.

The orchestrator enforces these boundaries in task selection, decomposition, file ownership, and review. If a task depends on work outside its boundary, create or route the dependency issue to its owner, record it in `.agent-state/project-state.md`, and continue with other in-scope work. Do not widen scope by silently reading another area. If no independent work remains but a cross-workstream dependency is pending, apply the waiting policy above instead of exiting. Stop only under the documented stop conditions or at a configured per-invocation limit.

These are agent workflow rules, not an operating-system security boundary. The clones contain the public monorepo and the containers have outbound network access; a determined process could retrieve other public files. Do not claim filesystem-level isolation unless the container mounts and repository layout actually enforce it.
