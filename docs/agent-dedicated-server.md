# Роль рабочей области: выделенный сервер

## Назначение

Эта рабочая область отвечает за Rust-сервис регистрации и начального подключения клиента к кластеру. Нормативные требования находятся в [общем дизайне и межобластных требованиях](specification-v1.md) и в [SRS выделенного сервера](specification-v1/dedicated-server.md). SRS — единственный источник требований к функциям, качеству, ограничениям и критериям проверки.

## Границы ответственности

Работай в `dedicated-server/` и отвечай за явно назначенные общие файлы репозитория. Общие файлы включают корневые файлы и общие каталоги `.github/`, `.opencode/`, `contracts/`, `docs/`, а также Dockerfile и Compose-конфигурацию. Issue на общий файл должен иметь метки `area:dedicated-server` и `agent:claimed/dedicated-server`, а в задаче должны быть перечислены точные пути. Не читай исходники Android, storage-узлов или тестовой среды и не меняй их файлы. Используй SRS и опубликованные контракты как основание взаимодействий. Не расширяй сервис за рамки поведения, заданного SRS.

## Правило постановки и выполнения задач

По решению владельца от 2026-10-30 dedicated-server — единственный ответственный за общий SRS, `contracts/` и корневые инструкции/конфигурацию. Указание из ревью от 2026-10-28 о передаче общих документов distributed-server отменено. Принимай задачи на общие контракты от остальных областей через issue с точными путями и requirement IDs; спецификации областей и их реализация остаются за соответствующими областями.

Приоритет по отчётам: реализовать уточнённые требования [protocol-details.md](specification-v1/protocol-details.md) и [configuration-profile.md](specification-v1/configuration-profile.md), подготовить общие wire/configuration fixtures TST-105–109. OPEN-003/017 закрыты: регистрация, чтение реестра, атомарный replay и failover больше не требуют локального выбора схемы. Подготовь потребителям контракт и векторы через обычный PR-процесс; готовность своего listener не является предварительным условием. Изменение схемы требует отдельной ревизии SRS. Это план реализации, а не новый источник продуктового поведения.

Каждая задача реализации должна ссылаться на точные ID и редакции требований SRS, которые она выполняет; тестовая задача также указывает связанные `TST` требования. Не выводи поведение продукта из этого брифа, GitHub issue, комментария ревью или ежедневной заметки. Если нужного требования нет, оно неполно или конфликтует с другим, сначала подготовь изменение SRS отдельной задачей; реализацию начинай после слияния этого изменения.

Регистрационная команда нового аккаунта должна охватывать аккаунт и первую установку атомарно согласно общим `FR-DED-038/039`; приёмочные fault-сценарии заданы `TST-093`. Учитывай это при проектировании оставшегося межсерверного контракта.

Результат успешно зафиксированной регистрации хранится по `(логин, request_id)` в реплицированном реестре без TTL в v1 и применяется атомарно с регистрацией (`FR-DED-040`–`FR-DED-042`). Это сохраняет идемпотентность после перезапуска и snapshot recovery; сервер не должен создавать новую установку при таком повторе (`FR-DED-005 / 2`).

Временные отказы регистрации не являются окончательным результатом: повтор с тем же request_id возвращает committed успех либо повторяет попытку. Не считай таймаут доказательством отсутствия commit; однократность применения обеспечивает state machine (`FR-DED-043`–`FR-DED-045`, `TST-096/097`).

Команда фиксации регистрации может поступить от dedicated на любой storage-узел: follower передаёт её лидеру внутри защищённого кластера и возвращает результат по исходному соединению, без redirect dedicated (`FR-DED-046`–`FR-DED-048`, `TST-101`). Учитывай этот маршрут при реализации своей стороны контракта.

При временном отказе storage-узла dedicated сам перебирает другие узлы с неизменной регистрационной командой в пределах общего deadline, числа попыток и задержек; окончательные ошибки запроса не повторяются (`FR-DED-049`–`FR-DED-053`, `CFG-CL-042`–`CFG-CL-045`, `TST-102`–`TST-104`).
