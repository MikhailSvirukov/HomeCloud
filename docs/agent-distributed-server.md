# Роль рабочей области: распределённые storage-узлы

## Назначение

Эта рабочая область отвечает за Rust storage-узлы, хранилище и их кластерные взаимодействия. Нормативные требования находятся в [общем дизайне и межобластных требованиях](specification-v1.md) и в [SRS storage-кластера](specification-v1/storage-cluster.md). SRS — единственный источник требований к функциям, качеству, ограничениям и критериям проверки.

Каждый distributed-server — полноценный voting-узел Raft. Его процесс выполняет локальный экземпляр OpenRaft: участвует в выборах и консенсусе, принимает и отправляет RPC другим storage-узлам, сохраняет Raft-состояние и применяет committed-записи к state machine. Основание — `FR-CL-001`, `FR-CL-006`, `FR-CL-009/010`, `FR-CL-016/017`, `FR-CL-020`, `FR-CL-030/031` и `NFR-MAINT-001`–`NFR-MAINT-004`. Выделенный сервер не является Raft-участником. Blob-репликация выполняется отдельно от Raft-журнала (`FR-CL-011`).

При планировании и ревью отдельно проверяй интеграцию локального consensus runtime, транспорта, постоянного Raft-хранилища и state machine. Наличие сериализатора RPC, сетевого канала, трейтов или моков само по себе не завершает требования консенсуса. До завершения runtime-интеграции сохраняй соответствующие требования незавершёнными в карте состояния; проверку реальных выборов, commit, потери кворума и восстановления проводи через PR CI.

## Границы ответственности

Работай только в `distributed-server/`, кроме явно назначенных общих файлов. Не читай исходники Android, выделенного сервера или тестовой среды. Используй SRS и опубликованные контракты как основание межкомпонентного поведения. Не вводи несовместимые локальные изменения сетевых интерфейсов.

## Правило постановки и выполнения задач

Каждая задача реализации должна ссылаться на точные ID и редакции требований SRS, которые она выполняет; тестовая задача также указывает связанные `TST` требования. Не выводи поведение продукта из этого брифа, GitHub issue, комментария ревью или ежедневной заметки. Если нужного требования нет, оно неполно или конфликтует с другим, сначала подготовь изменение SRS отдельной задачей; реализацию начинай после слияния этого изменения.
