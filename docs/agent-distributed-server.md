# Задание агенту: распределённые storage-узлы

См. [общую спецификацию](specification-v1.md). Реализовать фиксированный multi-node кластер с Raft и отдельной репликацией файлов. Storage-узлы напрямую соединяются друг с другом; выделенный сервер не ретранслирует Raft- или data-plane-трафик. Исходный целевой стек серверов — Rust; конкретный набор библиотек выбирается с учётом совместимости протокола. Предварительные идеи из наброска: Tokio для TCP/async задач, отдельный путь для дискового I/O, bounded buffers/pools и пул CPU-задач для сжатия/криптографии. Это варианты для оценки, а не нормативное требование v1.

## Модель исполнения

- Реализовать узел как один Rust-процесс с акторным взаимодействием внутренних компонентов.
- Tokio обслуживает TCP-соединения и координацию; `tokio-uring` не использовать.
- Один выделенный OS thread на узел владеет `io_uring` и принимает команды через bounded channel. Не выполнять блокирующее ожидание completion на Tokio worker thread или в общем Tokio blocking pool.
- Дисковый актор может группировать операции по размерному лимиту или таймеру; конкретные значения определить профилированием.
- Сжатие/распаковка и криптографические операции выполнять в ограниченном CPU-пуле вне Tokio worker threads.
- Реализовать собственные асинхронные пулы крупных payload-буферов нескольких размеров с балансировкой; заголовки, управляющие кадры и metadata в эти пулы не входят.
- Обрабатывать file payload потоком ограниченных блоков; не держать весь файл в RAM. Ограничивать число буферов in-flight, применять backpressure и возвращать буферы после использования. Для больших данных поддержать логическую цепочку буферов и последний неполный блок.
- Учитывать отдельные пулы/классы для сжатого/зашифрованного входа и распакованного выхода. Расшифровку разрешено делать in-place при поддержке выбранной схемой; распаковка использует отдельный выходной буфер.
- При исчерпании буферов применять backpressure/ожидание или контролируемую ошибку, не допуская неограниченного роста памяти. Определить явное владение и возврат буферов. Передача по блокам не означает поддержку resume: после обрыва загрузка начинается заново с тем же `upload_id`.
- Не использовать общую `Mutex`/`RwLock` как механизм синхронизации горячего пути аллокатора. Аллокатор управляет I/O-буферами и не подменяет глобальный Rust allocator.
- Актор TCP-соединения только разбирает и собирает кадры, затем передаёт их следующему актору; аутентификация и обработка команд выполняются вне него.

## Требования

- Каждый узел имеет стабильный node ID/label, адрес, encryption key pair и signing key pair. Закрытые ключи сохраняются через перезапуск.
- Все межузловые сообщения шифруются гибридно и подписываются отправителем; ключи/подписи проверяются по bootstrap-топологии.
- При первом bootstrap существующий фиксированный набор узлов обменивается данными идентичности/ключами и уведомляет выделенный сервер.
- Новые узлы и изменение состава кластера не поддерживаются в v1.
- Действующий узел после временного отключения автоматически догоняет Raft-журнал/снимок и недостающие file objects.
- Большие файлы не помещать целиком в Raft-журнал. Raft фиксирует метаданные/ссылки, файловые blobs реплицируются отдельным data plane. Приём, запись и репликация payload выполняются потоком ограниченных блоков.
- Вычислять и проверять хэш исходного файла; принимать blob только после успешной расшифровки, проверки целостности и распаковки.
- Поддерживать учётные записи: выделенный сервер распространяет salted password verifier и открытый ключ клиента; каждый узел проверяет login/password локально на каждом запросе.
- Пароли не хранить и не логировать в открытом виде.
- Идемпотентность по `upload_id`: повтор операции возвращает прежний результат.
- Успех клиенту возвращать после долговременной записи файла на storage-кворуме и commit метаданных в Raft-кворуме.
- Не подтверждать запись на файл только на основании Raft commit метаданных.
- После commit недостающие узлы догоняют blobs фоном; возвращающийся узел получает пропущенные данные пакетами и проверяет хэши.
- Реализовать отдельные коды ответа для `NO_QUORUM`, временного timeout, ошибки credentials, повреждённого payload и нехватки места.
- Реализовать отдельный heartbeat endpoint для выделенного сервера. Это не Raft heartbeat; пропуски не изменяют конфигурацию кластера.

## Критерии приёмки

- Кворумные записи сохраняются при отказе допустимого числа узлов; без кворума клиент не получает успешное подтверждение.
- После потери ответа и повторной отправки прежний `upload_id` не создаёт второй объект/версию.
- После временного отключения существующий узел догоняет committed-журнал и file objects.
- Подмена payload или подписи обнаруживается до commit.
- Доступность heartbeat не влияет на участие узла в Raft и не распространяется клиентам.

## Не реализовывать

Динамическое добавление узлов, ротацию ключей, пользовательский download API, административную панель.
