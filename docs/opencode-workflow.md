# OpenCode workstream setup

## Layout

The monorepo has four workstreams: Android, distributed storage nodes, dedicated server, and test environment. `compose.yaml` starts one OpenCode container per workstream for a bounded run. Each container mounts its own clone of the same monorepo and separate OpenCode data/config volumes, so Git state and session history are not shared between workstreams. All four receive the DeepSeek API key from local `.env`; the key is not stored in the session volume. The clones use the same configured Git author/committer identity. The logical source areas are `android/`, `distributed-server/`, `dedicated-server/`, and `test-environment/`; shared instructions and published contracts are available in every clone.

## Bootstrap from an empty repository

Assume the public GitHub repository may initially contain no project files. The first backlog is repository setup, not feature implementation. Create separate, bounded bootstrap issues for the four owners. Each workstream orchestrator may create its own top-level directory and everything beneath it, including a local `AGENTS.md`, its build/workspace manifests, minimal starter documentation, and area-specific CI scripts/configuration. Establish independent project roots: `android/` (Gradle), `distributed-server/` (Cargo workspace), `dedicated-server/` (Cargo workspace), and `test-environment/` (Cargo workspace). Do not make a single root Cargo workspace that couples the Rust areas.

Bootstrap each area from the v1 specification and its own brief. The test-environment agent starts from the published specification/contracts and scaffolds its own workspace, mocks, and Docker-based harness; it does not wait for or inspect private implementation from the other areas. Component implementation can follow once the relevant public contracts exist.

Shared repository files such as root `AGENTS.md`, root README, common contribution guidance, and `.github/workflows/` are outside any one area’s default ownership. An orchestrator may create or edit a named shared file only when its issue explicitly assigns that file/path; it must not use that permission to inspect or change another area’s implementation. Keep each bootstrap issue/PR narrow (about 500–600 changed lines is the soft target), and split setup work when it grows. Keep each area's CI commands/scripts/configuration with that area. GitHub Actions workflow YAML must live under root `.github/workflows/`, so creating or editing it requires an explicitly scoped shared-infrastructure issue assigned to one workstream. That workflow should invoke the area-local checks and select checks based on changed paths plus shared-file changes. The normal reviewer and required-CI gates apply to bootstrap PRs too.

The initial backlog should cover: four area scaffolds with their own `AGENTS.md` and local CI checks; shared root guidance and repo entry-point docs; then a root `.github/workflows/` issue to connect those checks to required PR status checks. The operator may start only one workstream per daily cycle, so bootstrap issues are completed over multiple explicitly started cycles rather than all agents modifying shared root files in parallel.

The container images use OpenCode CLI 2.0.27. `Dockerfile.agent` has separate build targets: `android` installs JDK 17 and Android SDK API 36/build tools 36.0.0; `rust-agent` installs Rust 1.99.0, rustfmt, clippy, C/C++ build tools, OpenSSL and liburing development headers; `test-environment` adds Docker CLI and Compose. Versions are build arguments and can be overridden in `.env`. Compose gives each workstream its own Docker network, drops Linux capabilities, prevents privilege escalation, runs as UID/GID 1000, and mounts the feedback directory read-only. The project config is `.opencode/opencode.jsonc`; it defines one primary orchestrator, two implementation subagents, and one reviewer that cannot edit the checkout or merge. The orchestrator can launch only those three subagents. Workers cannot launch further agents. Every role uses the same GitHub account through one role-filtered MCP connection. Workers create PRs and read feedback; the reviewer posts review comments and an internal status marker; only the orchestrator merges. Because the PR author and reviewer are the same GitHub account, GitHub does not accept a formal approval from the reviewer role. The orchestrator reconciles reviews authored by `MikhailSvirukov` on merged PRs before planning. MCP tools are denied globally and enabled per agent. The GitHub token and DeepSeek API key are visible to commands/tests running as the same container user; role permissions limit model-invoked MCP tools, but this is still not an OS-level security boundary. Only trusted repository code should run in this setup. The orchestrator publishes text changes with GitHub MCP `create_branch` and `push_files`. Since the monorepo is public, local `git clone` and `git fetch` use anonymous read access. The orchestrator merges only after review approval and required CI pass, then records the result in the workstream's ignored `.agent-state/project-state.md`.

## Human code review feedback

Daily feedback is kept as separately numbered host-side files under `agent-feedback/reviews/YYYY-MM-DD-NN.md`. `agent-feedback/latest-review.md` points to the newest note; it and `standing-guidance.md` are mounted read-only into every container. At startup, orchestrators and reviewers read all files for the newest date in ascending filename order, plus the latest pointer and standing guidance. The directory is ignored by Git, so personal review notes stay out of the public monorepo. Add concise notes under Keep / Change / Avoid and mark whether they apply globally or to one workstream. For exact code-line feedback, use GitHub PR review comments. GitHub Discussions are an alternative for public team-wide feedback. Repeated preferences may be moved into tracked `AGENTS.md` or role guidance only after the owner approves them. The notes are included as context each run; this does not train or permanently update a model.

## Manual GitHub issue intake

When an orchestrator is explicitly started for a workstream, it lists open repository issues, then reads candidate issues in detail (title, body, labels, and assignment status). It decides ownership from the issue text and the workstream map, never by browsing another workstream’s implementation. An issue is eligible for implementation pickup only if it cites existing SRS requirement IDs marked `MUST / Утверждено` and those requirements do not depend on unresolved `OPEN` decisions, or if it is an explicitly scoped repository/process-maintenance task. If an issue requests product behavior not covered by the SRS, is ambiguous, incomplete, or conflicts with it, treat it as a specification-change request; do not implement it from issue wording. Create or report a separate SRS-change task first. The first clearly in-scope, unassigned eligible issue is available for pickup. Issues assigned to a person or labeled `agent:do-not-pick` are skipped. A claim label for another workstream is skipped; a matching `agent:claimed/<workstream>` label means resume that workstream’s existing issue. If the issue spans workstreams or ownership is unclear, leave it untouched and report its number to the operator.

Before work, the orchestrator rechecks that the issue is open and either unclaimed or claimed by this same workstream, preserves existing labels, then adds `area:<workstream>` and `agent:claimed/<workstream>` (for example `area:android` and `agent:claimed/android`). It re-reads the issue to confirm the claim. These labels are the GitHub-visible assignment to an agent workstream; the container does not have its own GitHub user identity to assign as a person. The owner should create these labels once in repository settings. Only one workstream runs per daily review cycle, which is the primary protection against two orchestrators claiming the same issue; labels are a visible claim marker, not an atomic lock.

If no suitable owner-created issue exists, the orchestrator may create one issue for its planned PR. It must not create a duplicate when it picked up an existing issue. For implementation work, the task and PR must cite the exact SRS requirement IDs/revisions; the issue title/body remain a short human-readable problem description without acceptance criteria, implementation plan, or test-status line. For a specification-change task, identify it as such and edit the appropriate SRS with complete, uniquely identified, objectively verifiable requirements before implementation is scheduled.

## Work and GitHub flow

1. The orchestrator reads `docs/agent-global.md`, the current daily review notes, candidate open issues, the scope brief selected by `AGENT_SCOPE`, the common v1 specification, and only the assigned area SRS. For Rust work, all agents read the root `AGENTS.md` first. It verifies that the issue maps to existing requirement IDs or is a repository/process-maintenance task before claiming it. A new or unclear product behavior goes through an SRS-change task and PR before implementation.
2. The orchestrator decomposes the selected requirement IDs into one or more independent, bounded worker tasks. Each task gives its exact requirement IDs/revisions, owned paths, expected change, and relevant verification. Test tasks reference the corresponding `TST` IDs and behavioral requirements. Workers must not add behavior or tests without an SRS basis. Aim for no more than about 500–600 changed lines in the complete PR, including tests; this is a soft upper target. Use smaller worker tasks when two workers contribute to the same PR. Assign disjoint file areas when workers run concurrently.
3. Workers implement their assigned task and write relevant unit/integration tests. The orchestrator integrates the changes and runs the relevant checks.
4. The orchestrator fetches `origin`, creates a local topic branch from the updated default branch, and creates the matching remote topic branch with `github_create_branch`. After local checks pass, it publishes changed text files through `github_push_files` (and deletions through `github_delete_file`) to the task branch.
5. The responsible worker creates the PR linked to the issue through `github_create_pull_request`, using the same GitHub account as every other role. The PR description lists the requirement IDs/revisions addressed (or identifies the SRS change) and explains any deviations or deferred coverage. The reviewer checks requirement traceability and posts findings as a `COMMENT` review, including `[agent-review: changes-requested]` when fixes are needed. The worker reads the review, fixes assigned files, and reports the update; the orchestrator publishes it to the same branch and asks for another review. When clean, the reviewer submits a `COMMENT` review containing `[agent-review: approved]`. GitHub will not accept an official approval from the PR author, so this marker is an internal workflow status. The orchestrator checks the marker and required CI before merging. Branch protection requiring a formal approval from another user cannot be met by this single-account setup.
6. The orchestrator records issue/PR links, merge commit, current state, and next work in the container's persistent `.agent-state/project-state.md`.

## Scope boundaries

Each container has a separate clone, but each clone contains the public monorepo. The workstream restriction is therefore an agent workflow rule, not a filesystem security boundary. Every orchestrator, worker, and reviewer must read `docs/agent-global.md` and stay within the assigned logical source area. The orchestrator must give workers explicit paths, delegate only within its workstream, and review only its own workstream diff. Agents must not browse, search, list, summarize, or adapt to another workstream's implementation. All four workstreams may read the shared global instruction, v1 specification, their own brief, published contracts, and daily feedback. For Rust work they may also read root `AGENTS.md` for language practices. Shared root manifests or files may be accessed only when needed for the assigned task, with the dependency reported to the orchestrator.

The test-environment workstream is the limited exception: it may inspect public Rust traits/types and public Kotlin protocol/API interfaces needed for mocks, fakes, and integration tests, but it must not depend on private component implementation. If a contract is missing or incompatible, report it to the owning workstream rather than opening or changing its implementation. A contract change must be proposed through the normal issue/PR flow.

## Work budget

Start work only after an explicit operator request. The operator starts one workstream with `docker compose run --rm <service>`; the container is removed after OpenCode exits, while host checkouts and named volumes persist. Each invocation uses `AGENT_MAX_TASKS` (default 20) and `AGENT_MAX_RUN_SECONDS` (default 3600) from `.env`; the limits apply to that invocation. Count an item when its issue is claimed, and keep at most one active issue/PR cycle at a time. After each merge, the orchestrator may claim the next clearly in-scope issue if both limits allow. Start only one workstream per daily review cycle. The time limit remains a model-instructed soft cutoff, not a forcibly enforced container timeout. If time expires during an issue, record progress and blockers at a safe checkpoint and wait for the next explicit operator run; do not claim another issue.

## Prepare local checkouts

The public repository is checked out at `HomeCloud/`; the Compose/control directory is its sibling `backup/`. The four separate workspaces are cloned under `../homecloud-clones/`: `android`, `distributed-server`, `dedicated-server`, and `test-environment`. These paths are configured in `.env` and may be changed there.

Before each task, the orchestrator fetches the public `origin` and creates a fresh local topic branch from `DEFAULT_BRANCH` (defaults to `main`). It creates the matching remote branch with GitHub MCP. The orchestrator commits the local changes before publishing through MCP. After merge, the orchestrator fetches `origin`, switches to `DEFAULT_BRANCH`, and uses `git reset --keep origin/DEFAULT_BRANCH` to update the clean checkout. Do not mount the same checkout into more than one OpenCode container.

## Run

1. Install Docker Engine/Desktop with Compose and make sure the host can pull the OpenCode image.
2. The four clones already exist at `/home/mikhail/workdir/homecloud-clones/<workstream>`; verify they track the same public `origin` and `main` branch. Their Compose paths are set in `.env`.
3. Copy `.env.example` to `.env`, fill `GITHUB_MCP_TOKEN` with a fine-grained PAT scoped to this repository, set `DEEPSEEK_API_KEY`, and set the branch/clone paths if needed. Compose passes the provider key to OpenCode as an environment variable; it is not stored in the repository or the agent session volume.
4. Build the image with `docker compose build` after the language toolchains and isolated test engine have been added.
5. Start only the selected daily workstream with `docker compose run --rm android` (replace the service name as needed). Compose runs `opencode run --continue --agent orchestrator --auto` without a TUI. Each service has a separate session volume and resumes its own latest session; the host checkout and `.agent-state` also persist. The run reads every review note for the newest date, obeys the configured task and time limits, prints a summary, and exits.

Agent containers do not mount the host Docker socket. The optional `compose.test-engine.yaml` starts a separate TLS-protected Docker-in-Docker daemon for the test agent; it requires `privileged` mode and should be used only for trusted test code. Start it with `docker compose -f compose.yaml -f compose.test-engine.yaml run --rm test-environment`, then stop/remove the DinD service with `docker compose -f compose.yaml -f compose.test-engine.yaml down`. Android builds and JVM unit tests have their JDK/SDK in the image; connected Android tests still need an external emulator or physical device.

## Current setup limits

The control directory `backup/` is not a Git repository; the public Git repository is `HomeCloud/`, initialized on `main` with `origin/main`. Its four separate clones are under `homecloud-clones/`. The initial remote commit contains only `LICENSE` and `README.md`, so publish the bootstrap files and update all four clones before starting agents. Docker CLI 29.9.0 is present; verify daemon access for the account running Compose. Full Android connected tests need an external emulator/device. Docker integration tests use the optional privileged DinD service and generated TLS client certificates; the host Docker socket is never mounted. Test commands run as the OpenCode UID and can access that container's GitHub token environment, so only trusted repository code should run in these containers.

## GitHub MCP permissions

One role-filtered GitHub MCP connection uses the owner’s account for every role. The orchestrator can list merged PRs and read review bodies/comments authored by `MikhailSvirukov`; workers get `github_create_pull_request` and `github_pull_request_read`; the reviewer gets `github_pull_request_read`, `github_pull_request_review_write`, and `github_add_comment_to_pending_review`. Workers cannot write reviews, manage issues, publish files, or merge. Do not add broad `github_*` allow rules.

The four Compose networks isolate the services from one another while retaining outbound access needed for GitHub and package downloads. All containers run unprivileged with no Linux capabilities, no-new-privileges, and a read-only root filesystem; only the checkout, OpenCode state/config, tool caches, feedback file, and `/tmp` have write access. No Docker socket is mounted.

The source-level boundary is instruction-level: each container mounts a full monorepo clone, so a determined agent or test command could still read another workstream's files or fetch the public repository. The orchestrator and role prompts must enforce the scope policy in `docs/agent-global.md`; this is not an OS-level access control. If stronger isolation is needed later, use restricted source mounts or separate repositories plus network/tool restrictions. The test harness may read only public Rust traits/types and Kotlin API contracts, as requested.

These OpenCode permissions govern which MCP tools each model agent can call; they are not an OS security boundary. The GitHub PAT is present in the OpenCode process environment to populate the remote MCP Authorization header; shell commands and tests under the same UID may be able to read it. Tests can also access that container's OpenCode data/config volumes and outbound network. The current setup is suitable only while repository code and tests are trusted. A credential-free build/test runner plus a separate MCP credential broker is required before treating agent code as untrusted. `push_files` accepts file contents as text, so binary-file changes need a future Git transport path. Renames can be represented as a new text file plus `delete_file`. Do not mount a host SSH-agent socket into these containers: workers and tests share the container user and could use its key.
