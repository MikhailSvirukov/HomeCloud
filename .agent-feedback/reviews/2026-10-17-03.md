# Daily review — 2026-10-17 — 03

## Keep
- Разделять требования, которые проверяют сам harness и fault-injection-инфраструктуру, и сценарии, проверяющие поведение реальных компонентов.
- Использовать опубликованные контракты для межкомпонентных проверок и не привязывать test-environment к внутренностям реализаций.
- Разделять ограничения среды выполнения агентов и незакрытые продуктовые или архитектурные решения.
- Считать SRS нормативным источником требований: реализация должна следовать зафиксированному 4-байтовому big-endian префиксу кадра и настроенному пределу кадра.

## Change
- Test-environment должен продолжать независимую работу без ожидания готовности всех остальных компонентов. Для разработки и проверки управления Docker, сети, lifecycle и volumes допускаются тестовые fixture-образы; они не заменяют реальные образы как критерий готовности интеграционных сценариев.
- Разделять блокеры по требованиям: реальные серверные образы нужны для сценариев запуска и проверки поведения серверного кластера; Android-сценарии требуют клиент и подходящее устройство/эмулятор; сценарии управления инфраструктурой и fault injection разрабатываются отдельно.
- Если техническое решение для `TST-006` не задано, test-environment orchestrator должен выбрать и обосновать способ выборочного ограничения сетевой связности, оформить необходимое изменение требований отдельным PR и продолжить без ожидания одобрения владельца.
- Отсутствующие общие контракты нужно маршрутизировать их владельцу (`dedicated-server` для общих путей), указать точные зависимые TST IDs и продолжать независимые задачи. Не объявлять весь test-environment заблокированным из-за отсутствующих компонентных образов.
- Android-workstream должен продолжать задачи, полностью определённые текущими требованиями: адаптер источника медиа на `ContentResolver`, адаптер метаданных на Exif/MediaStore, цикл WorkManager с долговечной очередью, foreground-передачу типа `dataSync`, обработку `POST_NOTIFICATIONS` и сжатие Zstandard в цепочку payload-буферов (`CON-AND-001`–`CON-AND-006`, `FR-AND-035/036`, `FR-UP-001/002`).
- Android setup и основной экран можно реализовывать через существующие интерфейсы и моки до готовности сетевой интеграции. Реальное подключение к регистрации и топологии зависит от соответствующих опубликованных серверных контрактов; эта зависимость не должна блокировать независимые UI и application-layer задачи.
- `OPEN-003` относится к оставшимся схемам CBOR и межсерверным сообщениям: Android orchestrator должен зафиксировать конкретные зависимости Android от ещё не опубликованных клиентских схем, назначить их владельцу и продолжать остальную работу. `OPEN-017` (диапазоны/defaults конфигурационных значений) и `OPEN-022` (численные цели после прототипа и замеров) не являются общим основанием для остановки Android-workstream; выбираемые сейчас значения конфигурировать и оформлять решения по процессу изменения SRS.
- Distributed-server orchestrator должен самостоятельно разрешить `OPEN-007`: выполнить прототип fixed-membership OpenRaft integration, выбрать и обосновать версию crate и сериализацию RPC, записать решение изменением SRS в отдельном PR, пройти обычные внутреннее ревью и CI, смержить PR, затем продолжить реализацию отдельным PR без ожидания одобрения владельца.
- Рассматривать `io_uring_setup = EPERM` в agent container как ограничение среды выполнения, а не как пробел требований продукта. Отдельно диагностировать Docker seccomp и host `kernel.io_uring_disabled`, зафиксировать точную причину и применить узко ограниченную настройку runtime. Пока подходящая среда настраивается, продолжать работу, не зависящую от фактического вызова `io_uring`.
- Сохранять требование `io_uring`. Любой fallback backend, который должен войти в продукт, сначала оформить как отдельное решение по SRS; не заменять `io_uring` молча ради прохождения тестов в ограниченном контейнере.

## Avoid
- Не останавливать весь workstream с общей формулировкой «нужны рабочие версии всех компонентов», если часть требований не зависит от них.
- Не считать fixture-образы достаточной проверкой требований, которые прямо требуют интеграции с реальными компонентами.
- Не заявлять требования к кадрированию нерешёнными, если реализация расходится с `INT-NET-002`–`INT-NET-004` и `CFG-CL-011`.
- Не останавливать весь distributed-server workstream только потому, что текущий контейнер не может выполнить `io_uring_setup`.

## Example
- Независимая инфраструктура: `TST-002`–`TST-006`, `TST-009`, `TST-017`.
- Интеграционные сценарии требуют реальные компоненты только там, где проверяется их поведение: например, `TST-001`, `TST-008`, recovery и протокольные требования.
- Android может реализовывать scanner adapters, WorkManager cycle, очередь, уведомления и Zstandard до появления серверной сетевой интеграции; точные внешние схемы/регистрация/топология остаются контрактными зависимостями.
- `OPEN-007`; `INT-NET-002/1`–`004/1`; `CFG-CL-011/1`; `ARCH-NODE-004/1`–`005/1`.
- Dedicated-server должен выполнять независимую observability-работу по `NFR-OBS-002`, `NFR-OBS-004`, `CFG-OBS-001/002`: важные runtime-события; конфигурируемые путь и retention логов; bounded non-blocking file writer с loss counter; ротация по размеру и возрасту. Для старта определить и задокументировать двухфазную инициализацию, поскольку конфигурация загружается до того, как известен путь лог-файла. Не превращать логи в запись каждого действия.
- Реализовать метрики по `NFR-OBS-005`–`NFR-OBS-008` и `CFG-OBS-003/004` через Prometheus `/metrics`; выбрать и обосновать доступность endpoint (loopback либо TLS) согласно требованиям и модели развёртывания, ограничить cardinality меток и документировать выбранные метрики.
- После публикации wire contract реализовать wire-layer на его основе. До интеграции регистрации, topology, heartbeat и распространения verifier/ключей на storage nodes закрыть относящиеся к этому решения `OPEN-003` и `OPEN-007` отдельным SRS-change PR: dedicated-server владеет общим SRS, поэтому его orchestrator должен сформулировать обоснованный вариант, проверить влияние на потребителей, получить обычные внутреннее ревью и CI, смержить решение и затем продолжить реализацию отдельными PR без ожидания одобрения владельца.
- Не считать весь dedicated-server workstream заблокированным контрактными решениями: observability и другие требования с опубликованными критериями остаются выполняемыми параллельно. Для каждой реально зависимой задачи указывать точный requirement ID и конкретную отсутствующую схему/контракт.
- Блокеры фиксировать на уровне конкретной задачи: указывать зависимые requirement IDs, отсутствующее решение/контракт или ограничение среды и что именно из-за этого нельзя выполнить. Открытое решение может остановить только зависящую от него реализацию; orchestrator должен запустить его закрытие по процессу изменения SRS и продолжать независимую работу. Не объявлять workstream целиком заблокированным, пока остаются подходящие задачи.
